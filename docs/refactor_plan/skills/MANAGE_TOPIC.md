# Manage Topic

## Topic Flow
1. Create Topic if not exist
2. Walk through part by part, 
 - Each part contains sections. Each section:
    - Explain section
    - Ask checks for section
    - If needed, record mistakes
 - Practice part
    - Ask practice questions
    - If needed, record mistakes

## Creating Topics

Steps:
1. Create scratchpad name.
2. Create topic (`createTopic`).
3. Source topic parts, identify [What needs to be understood](WHAT_IS_UNDERSTANDING.md) given each part.
4. Propose Plan, ask use for confirmation.
  - User confirms, proceed to walking part by part.
  - User declines, make changes.

### Sourcing Topic Parts
Prioritise the creation topics using the following:
1. If have Attached Sources. Create the topic parts using the attached sources.
2. Else, use web search to find a walkthrough.

If there are multiple flows, you can merge flows.

## Explaining
[Explain in this style](WRITING_STYLE.md).

## Asking Checks and Questions

2 Scenarios,
1. Walking through a topic (Checks)
2. Practice after a topic part (After 1)

Always go question by quesiton, it is dynamic what quesitons can be asked so no "Fixed Test Set".

Record each check and follow-up once with `topic_recordQuestion`. Select its recorded step with `pendingCheck` in `save_learning_state`. The app displays the question.

### 1. While walking through a topic
Topic evaluation happens as the topic is being walked through. 

1. While walking through, if the source material (i.e. slides/textbook walk throughs) poses a question OR examples, ask.
2. Ask for the main idea in their own words; assess it with [What is understanding](WHAT_IS_UNDERSTANDING.md).

### 2. Practice after topic part
Can happen right after (1) of a topic part OR at the end of the topic.

1. Retrieve the topic's questions (`getQuestions`)
2. Source Questions

Prioritise the following to source questions. 
1. Source questions from attached assets (NOT FROM WALK THROUGHS). Move to (2) IF the question was asked previously / None available AND was answered correctly.
2. Source questions from the internet. Move to (3) IF the question was asked previously. 
3. End of practice

## Feedback and Deliberating
After the user answers, give [FEEDBACK and DELIBERATE on the answer](FEEDBACK_AND_DELIBERATE.md)

Afterwards, document mistakes for the part in the state file.

## Maintain Scratchpad

Explain the subject through one worked example that grows with the lesson. Name sections after the concepts or example's goal, and start directly with its inputs or explanation. Keep assessments of who said or understood what in structured progress and private handoffs.

1. Choose an example that can connect the topic's parts. Use a source example or create one that illustrates the concepts; distinguish invented inputs from source data. Establish its goal and concrete inputs on the first teaching turn, including an overview section.
2. For each taught section, explain its contribution to that same example. Show the relevant inputs, working, result, and why the result illustrates the concept. For structure, flow, layout, or quantitative relationships, make the explanation visual: use original labelled Mermaid diagrams, field tables, or Plotly plots with the example's values; use source figures when examining them. Explain what to observe and evolve the visual with the example.
3. Match the detail to what has been taught: an overview establishes the example's setup and demonstrates the broad idea; later sections develop its implementation and calculations. Develop only taught concepts and keep answers to pending checks private.
4. Extend the existing walkthrough with each lesson. Preserve the example, previous working, and useful source links; revise the relevant step after a mistake or clarification. Retain required source examples where taught, connecting them back to the overarching example. Add other examples only when a concept cannot naturally fit.

Before saving, read the accumulated walkthrough: every taught section must connect to the example with concrete working or an illustrated explanation. Section summaries and a promise to add an example later do not meet this requirement. Follow the topic template; keep prose direct without removing the explanation needed to follow the example.

## Structured content

`scratchpad.state.json` owns the curriculum, explanations, terminology and learning evidence. `scratchpad.md` is generated by the app.

Read the current state before changing content. Use `topic_editContent` with an ordered `changes` array:
- `add`: supply a new block with a unique stable ID. Use `afterId` to place it after another block, or `afterId: null` to place it first.
- `edit`: supply the complete replacement block with the existing ID.
- `delete`: supply the existing block ID.

All changes in one call succeed together. Keep IDs stable across wording changes. Use `sectionId` to associate an explanation with its curriculum part. Use a `source` block with `materialId`, `page` and `presentation` (`link` or `image`) for a citation or slide. Use a `term` block with `term` and `meaning` for terminology.

Set `present` to the ordered block IDs to show in this turn's chat. The app renders those stored blocks, then the recorded check; do not supply a duplicate explanation in the final reply. For feedback that does not change stored content, use a normal final reply.

The app creates the directory, anchors, section headings, citations and final terminology table. Use `topic_updateTopic` for requested curriculum or metadata changes. Record questions, answers and progress with their dedicated tools. Keep private assessment keys in the chat handoff.
